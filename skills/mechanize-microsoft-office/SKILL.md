## Execution boundary

Use the [desktop skill](skill://mechanize-desktop/SKILL.md) for tool contracts and
consent. Author and change Office content through Mechanize MCP → Endly → native
GUI execution. Use freshly observed process/birth identity and exact current
window titles. Inspect welcome, account, activation, recovery or template screens
before assuming an editing canvas exists.

Prefer semantic controls, then a qualified scoped shortcut, then an advertised
capture-bound pointer route with fresh visual evidence. A rejected permission,
unknown input result or occluded window is not authority for an alternate route.
Do not force disabled canvas setters. A successful dispatch or surviving window
alone does not prove content, selection, save, recalculation or delivery.

For global keyboard or pointer operations, establish input ownership using the
user's current authorization and the runtime fence. Existing hands-off
authorization remains valid; do not repeatedly request the same interval.
Refresh content immediately before input, especially after a build,
restart or extended investigation. Unexpected content or focus changes require a
stop and observation; preserve user text and the original ledger. Do not repeat a
key or click to diagnose an uncertain outcome or rewrite its original predicate.

Keep qualification files as disposable copies and preserve original hashes for
preservation tests. Add an executable procedure only after actual MCP/Endly/native
execution and independent result checks. Optional saved-file inspection or
rendering must be within the user's authorized scope and cannot author, repair, or qualify GUI
behavior; see [the QA boundary](references/handoff-quality.md#independent-saved-file-qa).
